## 首次部署（按顺序）

0. **小程序后台 → 设置 → 用户隐私保护指引**：声明收集「头像、昵称」，用途填"展示在求助页和分享卡片上"。不配置的话，选头像、填昵称会直接失败
1. **建集合**（云开发控制台 → 数据库）：
   `users` `daily` `progress` `levels` `rescues` `rescue_help_pairs` `rescue_helper_attempts` `item_logs` `app_config` `completions` `stats_daily`
   - 权限全部设为**自定义规则** `{"read": false, "write": false}`。所有读写都走云函数（管理员权限不受影响），客户端直连数据库读不到答案
2. **导入数据**：`levels` 依次导入 `database/levels/` 下的四个文件（idiom / typo / poetry / xiehouyu），`app_config` 导入 `database/app_config.json`（格式选 JSON（控制台只认 .json 和 .csv 后缀；文件内容是每行一条记录））
3. **部署云函数**：开发者工具右键 `cloudfunctions/api` →「上传并部署：云端安装依赖」
   - 部署后再右键 →「上传触发器」，启用两个定时任务：每天 04:30 清理过期数据（`cleanupExpiredRecords`），每小时整点写入当天统计（`snapshotStats`）
   - `config.json` 同时声明了昵称内容安全检测需要的 `security.msgSecCheck` 权限
4. **建索引（必须）**：没有索引时，打开大厅、关卡页的查询会随数据增长变慢，定时清理也可能超时
   | 集合 | 索引字段 |
   |---|---|
   | `rescues` | `requesterOpenid` + `gameType` + `status` + `noticeSeen` |
   | `item_logs` | `createdAt` |
   | `daily` | `date` |
   | `rescue_help_pairs` | `date` |
   | `rescue_helper_attempts` | `date` |
   | `levels` | `gameType` + `levelNo` |
   | `progress` | `gameType` + `solvedCount`（降序）+ `lastSolvedAt`（升序），排行榜和通关统计都依赖它 |
   | `completions` | `gameType` + `completedAt`；`gameType` + `date` |
   | `stats_daily` | `gameType` + `date` |
5. **云函数超时时间**：控制台把 `api` 的超时时间从默认的 3 秒改成 10 秒（冷启动加多次数据库读写有可能超过 3 秒）

## 游戏规则配置表

所有游戏数值都在 `app_config` 集合的 **`game_rules` 文档**里，**在控制台改完立即生效，不用发版**。
文档里缺的字段会回落到代码默认值（`cloudfunctions/api/lib/rules.js`），所以可以只写想改的那几项。

**手改配置有保护**：每个字段都会检查类型和范围（例如次数必须是非负整数、奖励类型只能是 `hint` / `stamina`）。填错的字段**单独**退回默认值，其他填对的字段照常生效，并在云函数日志里打印 `[rules] invalid config fields`。开了广告但没填 `adUnitId` 时，会自动关闭广告。

## 闯关规则

**新手引导**：第一次点「开始挑战」时，先弹出玩法说明（体力、答错机会、提示与求助、怎么补体力），点「知道了，开始挑战」后才真正开始并扣体力。说明里的数字都来自当前配置。看过的记录存在本机（`utils/onboarding.js`），换手机或清理缓存后会再出现一次；之后随时可以在关卡准备页点「玩法说明」再看。玩法有大改动时，把存储键的版本号 `v1` 改成 `v2`，所有人都会重新看到一次。

```
进入未通过的关卡 → 点「开始挑战」，扣 level.staminaCost 点体力，获得 maxWrongAttempts 颗心
  中途退出再进来：继续本次挑战，不再扣体力
  答错：扣 1 颗心
  心扣完：挑战失败 →「再来一次」= 重新扣体力（这就是复活）
  已揭开的字跨挑战保留；已通过的关卡回看免费
  开始挑战前看不到题面，避免"先看题、想好了再开始"
```

### 道具不足时（提示和体力共用一套流程）

```
有余额 → 直接用
今天没打卡 → 弹窗打卡（一次发放全部打卡奖励）→ 自动重试
福利袋里有没开的宝箱（闯关宝箱 + 练习宝箱）→ 弹窗「去开宝箱」→ 跳到福利袋
视频开着 + 这种道具今天还没到视频上限 → 看视频，看完整才发奖 → 自动重试
（体力）今天练习还能攒体力 → 弹窗「去练习」→ 切到「趣味」
都不行 → 提示不足：引导求助好友；体力不足：告诉用户还有几分钟恢复 1 点
```

- **体力恢复自动到账**：每 30 分钟 +1，每天最多 15 点，页面只显示 `mm:ss 后送 1 点体力` 的倒计时，没有领取按钮。体力故意给得宽，玩不受限制；真正要省着用的是提示。以前攒在「待领取」（`users.staminaPending`）里的，下次结算时一起加进体力
- **福利袋 = 领奖励 + 每日任务**：上面是「每日任务 · 赚体力和提示」（打卡、今日挑战、自动恢复、看视频、数理乐园、九九神功、闯关开宝箱），每行显示今天的进度，到上限变灰但仍然展示；没到上限的可以直接点去做。下面是闯关宝箱和练习宝箱（`utils/welfare.js` 的 `buildTaskRows`）
- 体力恢复不靠定时任务：每次读写体力时，按距离上次结算过去了多少时间直接加进体力（`lib/items.js`）
- 「一天」按**北京时间**划分（云函数默认是 UTC 时区，见 `lib/date.js`）
- 道具的扣减和发放都在数据库事务里完成，多端同时操作也不会扣错
- 每笔道具变动都记在 `item_logs`（signup / checkin / ad / use / milestone / recovery / practice），用户反馈"次数不对"时按 openid 查这张表

## 过关激励

- **里程碑宝箱**：每通过 `milestone.everyLevels` 关解锁一个宝箱，奖励按序号递增：

  | 宝箱 | 1 | 2 | 3 | 4 | **5（大）** | 6 | 10（大） | 11 起 |
  |---|---|---|---|---|---|---|---|---|
  | 体力 | 10 | 12 | 14 | 16 | **36** | 20 | 56 | 30（封顶） |

  - ⚠️ 平衡提示：每 10 关至少返还 10 点体力，**一次过关的玩家体力几乎不减**，体力主要在挑战失败时消耗。觉得太宽松就调 `rewardRules.stamina.base`

## 多玩法

- **共用**：体力、提示、每日打卡、激励视频、配置里的闯关参数（体力消耗、答错次数、提示上限）和宝箱规则
- **各算各的**：关卡进度、段位称号、宝箱累计、排行榜、通关统计、收藏本
- 接口统一为 `game.*`，必须带 `gameType`（`idiom` / `typo` / `poetry` / `xiehouyu`），缺失或未知时返回参数错误
- 提示有两种方式（`lib/games.js` 的 `HINT_STRATEGY_BY_GAME`）：默认「揭开下一个字」；找错字是「排除错误选项」
- 新增玩法需要做的事：`lib/games.js` 注册玩法、解答字段和提示方式；`lib/rules.js` 加称号基线；`utils/games.js` 加前端展示文案；`scripts/level_builders/` 加一个生成器；`tests/levels.test.js` 加体检规则

## 控制中心（管理员在「我的」页进入）

- 全局开关，存在 `app_config` 集合的 `switches` 记录里（`cloudfunctions/api/lib/switches.js`），第一次拨开关时自动创建；和 `game_rules` 分开，重新导入 `app_config.json` 不会覆盖。云端每次请求现读，改完马上生效；玩家端的开关随登录信息下发（`utils/switches.js`），回到大厅刷新后生效

## 口算闯关、口算竞速、识字竞速（大厅的挑战）

「趣味」用来练习和探索，「大厅」用来挑战、上排行榜：数理乐园练会的内容，在大厅里比。两种玩法的题都由云端按种子生成并判对错（`cloudfunctions/api/lib/math-challenge.js`）；出题代码就是数理乐园的那套，由 `node scripts/sync_cloud_practice.js` 复制到 `cloudfunctions/api/lib/practice/`，`tests/boundaries.test.js` 会检查两份是否一致（改了 `utils/practice/skills`、`catalog.js` 或 `multiplication.js` 后记得运行）

- **口算闯关**（`gameType: math`，页面 `pages/game/math`，接口 `math.level` / `math.start` / `math.answer` / `math.hint`）
  - 关卡按数理乐园的推荐路线由易到难：分与合 → 10 以内加减 → 20 以内进退位 → 连加连减 → 比大小 → 100 以内加减 → 乘法口诀 → 表内除法 → 万以内加减，每个知识点 12 关（第 1–108 关）；之后是「全能挑战」，所有知识点混合、难题更多，一直闯到第 999 关
  - 一关 10 道题：7 道本阶段新题 + 3 道复习前面的；同一关所有人的题都一样。关卡不存数据库（不用导入），关数和阶段是固定的
  - 和其他大厅玩法同一套规则：开始扣体力，每次挑战可以错 2 次（第 3 次失败），答错停在本题；提示直接显示当前题的答案（扣 1 提示）；每 10 关宝箱、称号（口算小兵 → 口算状元郎，共 14 档）、排行榜按闯过的关数。暂不支持好友求助和收藏本
- **口算竞速**（页面 `pages/game/sprint`，接口 `sprint.islands` / `sprint.start` / `sprint.finish` / `sprint.board`，成绩存 `sprint_scores` 集合）
  - 先选岛屿（决定题目范围），60 秒能答多少答多少，答对答错都马上下一题
  - **得分 = 答对 − 答错**（最低 0 分）；同分时答错少的排前面，再相同按先达成的排前面
  - 排行榜每座岛一个，**默认每周一 0 点（北京时间）清零**，每人记本周最好的一次；控制中心关掉「排行榜每周清零」后改为历史总榜（两种成绩一直都在记，随时可以切回来）
  - 每次挑战扣体力，**默认 5 点**，控制中心「每次挑战扣体力」可改成 0–30
  - 防作弊：云端发题并记开始时间，交卷时按种子重新出题判分；超过 60 秒 + 8 秒宽限的不算，没答完整卷却提前 3 秒以上交的不算，平均每题快于 0.3 秒的不算
  - 没有提示，也不能求助好友，全凭自己；比赛中点返回会先确认（离开这局就作废）
- **识字竞速**（同一个页面 `pages/game/sprint?subject=chinese`，同一套接口和 `sprint_scores` 集合，规则、扣体力、周榜都和口算竞速一样）
  - 选一年级或二年级，每个年级一个榜；题目是汉字闯关的四选一题（看图识字、拼音选字、认偏旁、选字组词），每局 150 道不重复
  - 题库由 `node scripts/build_hanzi_sprint.js` 从 `database/levels/hanzi.json` 生成到 `cloudfunctions/api/data/hanzi-sprint-pool.json`（改了汉字关卡后记得运行，`tests/boundaries.test.js` 会检查）；挑战场列表在 `cloudfunctions/api/lib/sprint-tracks.js`，页面那份在 `utils/sprint.js`，两份也由 boundaries 测试核对

- **本周小结**（`packageMath/pages/weekly`，入口在「趣味」页荣誉卡片下方和地图顶部；接口 `practice.weekly`）：本周一到今天（北京时间）哪几天练过（数理乐园和九九神功都算，记在荣誉记录的 `practiceDates`，保留 14 天）、数理乐园答对题数和上周比、新拿的星星、抓回的小怪兽、本周新奖章、还在逃的小怪兽（可直接去抓）、九九神功练成几重，加一句喵算算点评。每日小账存在 `<openid>_math` 的 `days` 字段，只留最近 14 天。「分享给爸爸妈妈」把数字写在分享标题里，点开进「趣味」页，不打开孩子自己的数据。不做任何推送 / 订阅消息
- 荣誉（纯表扬，不发道具，面向小朋友；云端 `practice_stats` 里 `_id = <openid>_honors` 的一条记录，`lib/honors.js`）：
  - 🌺 小红花（数量在 `game_rules.honors.flowers` 里配置）：数理乐园每答对 10 题 +1、一轮连对到 10 题 +1；九九神功每重念完口诀 +1、练成 +1、三星 +1；每天第一次练习 +1
  - 🏅 奖章 22 枚：数理乐园 10 枚（含考试 3 枚）、九九神功 5 枚、坚持练习 2 枚（连续 3 / 7 天，按北京时间算）、岛主 5 枚。奖章由云端根据已有统计计算，达标即解锁，不能重复解锁

  - **加一枚奖章**：在 `lib/honors.js` 的 `MEDALS` 里加一行（`metric` + `target`）。如果要按新的维度算，先在 `METRICS` 里加一个指标函数。奖章 `id` 一旦上线就不能改

## 全部通关、统计与排行榜

- **"通关"只针对当前的最高关卡**：现在 1000 关，就是通过全部 1000 关；以后扩关，原来通关的人自动变回未通关，可以接着往下玩
- **全部通关提示**：通过最后一关时，过关页显示「恭喜通关全部关卡！更多挑战正在准备中，敬请期待」；关卡页和大厅也会显示已全部通关。界面上**不显示总关数**（大厅、关卡页、答题页只显示已通过的关数），只有管理员统计页会显示
- **通关记录**：每当有人打通当前全部关卡，就在 `completions` 写一条记录（用户、昵称、当时的关卡总数、日期）。同一个人在同一关卡总数下只记一次，扩关后再次通关会另记一条。目前只记录到数据库，不主动推送通知
- **统计**：
  - 通关率 = `progress.solvedCount ≥ 当前关卡总数` 的用户数 ÷ `users` 总数
  - 实时数据：管理员在「我的」→「数据统计」查看（通关率、最近 20 条通关记录、最近 30 天趋势）
  - 每日快照：定时任务每小时整点覆盖写入 `stats_daily` 中当天的那条记录，控制台可以直接查看
- **设置管理员**：在开发版或体验版里，到「我的」页长按头像那一行复制自己的 openid（正式版里只有管理员长按才会复制，防止孩子误触）（底部的「用户编号」只对管理员显示），在 `admins` 集合里添加一条记录：`{ "_id": "<openid>", "name": "备注是谁" }`，一个管理员一条。这张表和配置完全分开，导入 `app_config.json` 碰不到它。权限在云函数里校验，入口隐藏只是界面层面的处理
- **排行榜**：放在底部导航（大厅 / 排行榜 / 我的）。从关卡页、过关页点「排行榜」会直接打开当前玩法的榜单：底部导航页不能带参数，所以跳转前把玩法记在 `globalData.pendingLeaderboardGameType`，排行榜页显示时读取（`utils/navigation.js`）。按通关数排名，同分时先达到的人排在前面。展示前 `leaderboard.size` 名，在榜外的用户底部单独显示自己的名次，一关都没过的显示「暂未上榜」。前 N 名在每个云函数实例里缓存 1 分钟。接口不返回 openid

## 求助好友

- **发起不消耗任何东西，也不限次数**，但必须先开始过这一关的挑战（防止不花体力先看题面）。同一关只会有一条求助，重复分享也是同一条
- 每位好友对每条求助最多答错 `rescue.maxWrongAnswersPerHelper` 次，防止乱点试出答案
- 求助人自己先答对了，这条求助会自动关闭，好友点开会看到「TA 已经自己解开这一关啦」，不会占用好友的帮助次数
- 求助页显示的是求助人**当前**的头像和昵称，改资料后立刻生效
- 好友从卡片进入后能看到题目，看不到答案；第一个答对的人让求助人**直接过关**，不消耗体力
- **同一位好友每天最多帮同一个人解 `rescue.dailyLimitPerHelper` 关**。超出后，好友点开卡片会看到提示，请求助人换一位好友
- 限制放在好友答题这一步检查，因为分享时微信不会告诉我们卡片发给了谁，只有好友点开时才知道
- **分享本身不发任何奖励**：微信运营规范禁止"分享后获得奖励"（诱导分享）

## 头像与昵称

- **微信不再允许直接读取用户头像昵称**（2022 年 10 月起 `wx.getUserProfile` 只返回灰色头像和「微信用户」）。唯一的官方方式是「头像昵称填写」：点头像时微信提供「用微信头像」，昵称输入框（`type="nickname"`）的键盘上方会出现微信昵称
- **注册即有昵称**：服务端按 openid 生成固定的随机昵称（如「好学的小书童」，`lib/nickname.js`），头像用默认卡通头像，所以排行榜、求助页不会出现空白资料；历史上昵称为空的用户登录时自动补上
- **新用户首次进入大厅**弹出欢迎面板引导设置（只弹一次，记在本机）。点「先随便逛逛」就保留随机昵称；之后可在「我的 → 编辑资料」修改。用户亲自保存过资料后 `profileCustomized` 为 true，不再弹出
- 欢迎面板和「我的」页的编辑面板是同一个组件 `components/profile-editor`

## 安全与运维

- **昵称内容安全**：保存昵称时在服务端调用 `security.msgSecCheck`，只有结果为 `pass` 才保存；接口异常时也拒绝保存。头像使用微信的选头像能力，由微信负责检测
- **头像存储**：每个用户只能上传到自己的目录 `avatars/<用户哈希>/`，服务端拒绝其他路径；换头像时自动删除旧文件
- **定时清理**：每天 04:30 删除过期的道具流水、每日记录、求助计数
- **关卡总数缓存**：每个云函数实例缓存 10 分钟，导入新关卡后最多 10 分钟可见
- **提审风险**：体力、宝箱、段位都是游戏化机制，个人主体开不了游戏类目，审核可能认定为"小程序提供游戏服务"。建议部署后尽早用体验版提审一次；介绍文案和截图突出成语学习（释义、出处、成语本）

## 迁移设计（现在用云开发，以后可能迁到云托管或自建服务器）

**原则**：云开发专属的调用只允许写在下面几个「适配文件」里，业务代码只依赖它们。迁移时改这几个文件，页面和业务逻辑不用动。`tests/boundaries.test.js` 会检查这条边界，违反就报错。

| 层 | 适配文件 | 现在（云开发） | 迁移时改成 |
|---|---|---|---|
| 前端请求 | `utils/api.js` 的 `call()` | `wx.cloud.callFunction`，`{ action, payload }` 调同一个云函数 | `wx.request` 调 `https://<域名>/api/<action>`，带上登录凭证；返回结构 `{ code, message, data }` 不变 |
| 前端初始化 | `app.js` | `wx.cloud.init` | 删掉 |
| 前端上传 | `utils/upload.js` | `wx.cloud.uploadFile` 传到云存储 | 传到 COS / OSS（先找服务端要上传凭证） |
| 用户身份 | `cloudfunctions/api/index.js` | `cloud.getWXContext()` 取 openid | 校验登录凭证得到 openid（登录接口用 `wx.login` 的 code 换 openid）。业务函数只接收 `{ openid, payload }`，不用改 |
| 路由 | `cloudfunctions/api/index.js` 的 `ROUTES` | 按 `action` 分发 | 原样搬成 HTTP 路由，每个 action 一个接口 |
| 数据库 | `cloudfunctions/api/lib/cloud.js` 的 `db` / `_` | `wx-server-sdk` | 迁到云托管：换成 `@cloudbase/node-sdk` 连同一个数据库，查询写法基本一样。迁到自建数据库：要重写数据访问部分，这是工作量最大的一块 |
| 微信接口 | `cloudfunctions/api/lib/wechat-api.js` | 云调用（内容安全检查） | 用 access_token 调微信的 HTTPS 接口 |
| 文件存储 | `cloudfunctions/api/lib/storage.js` | 云存储删除文件；换出朗读语音的临时地址 | COS / OSS 的删除接口；语音改成 CDN 上的固定地址 |
| 定时任务 | `cloudfunctions/api/config.json` 的 `triggers` → `handlers/maintenance.js` | 云函数定时触发器 | 服务器上的定时任务，调用同样的函数 |

**迁移时还要处理的数据**：用户头像存的是 `cloud://` 格式的地址，只有云开发能显示。迁移存储时要把已有头像转存，并把 `users.avatarUrl` 改成 https 地址。

**开发约定**
- 所有业务都通过云函数完成，前端不直接读写数据库，所有集合的安全规则保持 `{"read": false, "write": false}`
- 身份只在云端取，不信任前端传来的 openid；权限（比如管理员）在云函数里校验
- 新的云开发专属能力（订阅消息、支付等）先加到对应的适配文件里，再给业务调用
- 可调的数值放进 `game_rules`，不要写死在代码里
- 字段名统一用驼峰（`createdAt`），不和下划线混用
- 查询都要带 `limit`，不一次读出整张表

**控制台要定期确认**：数据库每日自动备份、资源告警、云函数超时时间（定时统计和清理任务，数据量大了可能会变慢）。

### 数据来源与版权

两个开源项目都是 MIT 许可，但 MIT 只覆盖项目作者自己的整理工作，**不覆盖它们收录的词典原文**。所以：

- **成语释义全部是我们自己写的**（`scripts/data/idiom_explanations.json`，1015 条）。词典原文只用来查含义，不进题库；生成脚本遇到没有自写释义的成语会直接报错。已发布的关卡用 `python3 scripts/apply_idiom_explanations.py` 原地替换（只改释义和题面，关卡编号、答案、字盘不变），改完要把 `idiom.json`、`typo.json` 重新导入云数据库
- **成语出处**：古籍原句属于公有领域，保留；引用的是去世不满 50 年的现代作者作品的，出处留空（`level_builders/idiom.py` 的 `PROTECTED_AUTHORS`）
- **诗词**：只用了唐宋诗词原句、标题和作者，属于公有领域，没有用现代注释或赏析
- **歇后语**：民间俗语，只用了「谜面——谜底」和谐音标注

- [chinese-xinhua](https://github.com/pwxcoo/chinese-xinhua)：`idiom.json`（成语，只用来查含义、拼音和出处）、`xiehouyu.json`（歇后语）、`word.json`（汉字拼音，用于找同音字）
- 新华成语数据里的录入乱码（「◇」= 被吞掉的「，后」，以及个别 ↑ ◆ ★）在 `scripts/data/idiom_text_fixes.json` 里统一修正
- [chinese-poetry](https://github.com/chinese-poetry/chinese-poetry)：蒙学版《唐诗三百首》《千家诗》、全唐诗版《唐诗三百首》、《宋词三百首》、《全唐诗》、《全宋词》
- 原始数据下载到 `.cache/`（已加入 `.gitignore`，不入库），下载方式见 `scripts/build_levels.py` 顶部说明

### 各玩法的生成规则

**猜成语**（`scripts/level_builders/idiom.py`）
- `scripts/data/idioms.txt` 用 `# tier N` 分档（人工判断熟悉程度），同档内按用字生僻度排序
- 题面遮挡：答案的两字片段一律遮住；单个字只有生僻时才遮，常用字保留，避免题面满是 □；遮完仍露出 3 个及以上答案字的，就全部遮住
- 遮完仍读不通的题，在 `scripts/data/idiom_clue_overrides.json` 里手写题面（脚本会检查手写题面里有没有答案用字）

**诗词填空**（`scripts/level_builders/poetry.py`）
- 学段清单在 `scripts/data/poetry_stages.txt`，幼儿园到高中按部编版教材必背篇目人工整理；「进阶」自动收录唐诗三百首、宋词三百首里的其余作品
- **版本以课本为准**：取文本的优先级是 `scripts/data/poetry_supplement.json`（按课本手工补录的 24 首）→ 蒙学版唐诗三百首 → 千家诗 → 全唐诗版唐诗三百首 → 宋词三百首 → 全唐诗 / 全宋词。古籍里常见与课本不同的版本，例如全唐诗版《静夜思》是「床前看月光」
- 按**首句**匹配作品（古籍标题常与课本不同，如「钱唐湖春行」「池上二绝 二」），显示的标题统一用课本标题
- 异体字统一替换（穉→稚、遶→绕、徧→遍、篴→笛、沈舟→沉舟 等，见补录文件的 `variantReplacements`）
- 同一首诗的不同版本、开头一句相同的重复作品只保留一个；每首诗最多出几关由学段参数 `couplets` 决定
- 需要 OpenCC 做繁简转换，所以用 `.cache/venv/bin/python` 运行（`python3 -m venv .cache/venv && .cache/venv/bin/pip install opencc-python-reimplemented`）

**成语找错字**（`scripts/level_builders/typo.py`）
- 题目来源：`scripts/data/typo_common.txt` 里人工整理的常见易错成语（排在各学段最前），其余由脚本自动生成：在成语的某个位置换一个**同音常用字**
- 学段沿用猜成语的分档：第 1 档 → 小学，第 2 档 → 初中，第 3 档 → 高中，第 4、5 档 → 进阶
- 字盘 8 个字 = 正确字 + 7 个干扰字。干扰字依次取：正确字的同音字 → 错字的同音字 → 声母相同的常用字，只用常用字
- **两条硬性过滤**：错误写法如果被新华成语词典收录为异形词（如「莫明其妙」「走头无路」），整道题丢弃；字盘里的干扰字如果能拼出词典收录的写法，这个字不用
- **提示方式不同**：答案只有一个字，所以提示是「排除 2 个错误选项」，排除顺序在生成时固定（`eliminationOrder`）；每关最多 3 次，至少保留 2 个选项
- 需要额外下载 `xinhua/word.json`（汉字拼音）

**汉字闯关**（`scripts/level_builders/hanzi.py`，生成命令 `.cache/venv/bin/python scripts/build_levels.py hanzi <关数>`）
- 字池：教育部 2022 年《义务教育语文课程标准》附录常用字表的字表一（2500 字）里最常用、笔画最少的 1600 字，分 4 段各 400 字，前两段标「一年级」、后两段标「二年级」。按常用程度排，**不是按课本逐课排**
- 字频取自词典释义，会低估孩子日常用字（猫、跑、糖），所以 `scripts/data/hanzi_pictures.txt`（看图识字的图）和 `hanzi_words.txt`（孩子常用词）里出现的字都算最常用
- 每个字出一道题，题型轮换：有图的字出看图识字；其余在拼音选字、认偏旁、选字组词之间轮流。干扰字优先挑形近字（共用部件，如晴睛清请）和同音字
- 防歧义：拼音题排除任何读音（含多音字）相同的字；偏旁题的干扰偏旁不能出现在这个字里（「酒」不会出现在「哪个不是三点水」里）；组词题的干扰字填进去不能组成词典或常用词表里的词（`tests/levels.test.js` 也会检查）
- 需要的原始数据（放 `.cache/hanzi/`，不提交）：[字表一](https://gist.github.com/diaowinner/d78e9e9656619234298af5bc17302e44)（`table1.tsv`，对照[教育部原文](http://www.moe.gov.cn/srcsite/A26/s8001/202204/t20220420_619921.html)）、chinese-xinhua 的 `ci.json`（MIT）、[Make Me a Hanzi](https://github.com/skishore/makemeahanzi) 的 `dictionary.txt` 存为 `mmah-dictionary.txt`（LGPL-3.0，只在本机生成时用来拆部件挑干扰字，不随小程序发布）

**歇后语**（`scripts/level_builders/xiehouyu.py`）
- **全部人工挑选**，清单在 `scripts/data/xiehouyu_stages.txt`。原始数据有大量粗俗、别扭或多答案的条目，所以不自动收录
- 答案必须是数据源给出的答案之一；去掉括号里的谐音或释义，原始写法保留在 `note`，过关后显示（如「照旧（舅）」）
- 幼儿园到初中由人工按熟悉程度挑选；高中档挑的是历史和文学人物相关的条目。**歇后语没有教材可依，学段划分是主观判断**
- 每关有一句大白话的「意思」（`meaning`，自己写的，在 `scripts/data/xiehouyu_meanings.json`），答题前就显示在谜面下面，孩子可以从意思去猜后半句。意思不能把答案透出来：不能连着出现答案里的两个字，答案里的字最多出现一半（生成脚本和 `tests/levels.test.js` 都会检查）。改了意思后运行 `python3 scripts/apply_xiehouyu_meanings.py`，再用 Upsert 重新导入 `xiehouyu.json`；新挑的歇后语没写意思时，生成脚本会报错

### 生成与扩充（只追加）

```
python3 scripts/build_levels.py idiom 1000
.cache/venv/bin/python scripts/build_levels.py poetry 500
python3 scripts/build_levels.py xiehouyu 239
python3 scripts/build_levels.py typo 500
node tests/levels.test.js
```

- 扩充时把新内容写到对应清单的**末尾**（新档位或新学段），把目标关数调大后重新运行，再把整个 `.json` 导入 `levels` 集合，冲突处理选 **Upsert**
- **脚本的三条保护**（`scripts/level_builders/common.py`）：
  - 已有关卡逐字节保留，绝不重新编号、不改字盘。玩家进度是按关卡编号存的，一旦改动，所有人的进度都会错乱
  - 新内容必须比现有最难的关卡更难：放在更靠后的档位或学段，或者和最后一档同档但更难，否则脚本报错并列出这些内容
  - 目标关数小于等于现有关数时什么也不做，不会删除关卡
- 只有在**上线前**想整体重排时，才删除 `database/levels/<玩法>.json` 后重新生成
